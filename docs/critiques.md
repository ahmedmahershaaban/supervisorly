# Adversarial Critiques

Three independent critics attacked the synthesised foundation. Recorded verbatim so the
weaknesses stay visible rather than getting smoothed away.

---

## Scraping & data engineering

### Missing (23)

- **Research Information Management System (CRIS) adapters as a first-class tier: Elsevier Pure, Clarivate Converis, Symplectic Elements, VIVO, Haplo, Esploro** — The plan names only WordPress /wp-json and Drupal JSON:API. In the UK, Nordics, NL, DE, AU and much of Asia the faculty directory IS a Pure portal with a documented, uniform REST/OAI-PMH API (/ws/api/persons, /organisations, /projects, /research-outputs) and VIVO exposes RDF/SPARQL. One Pure adapter covers hundreds of institutions with identical schema including person↔project↔funder↔organisation edges — i.e. it fills Appointment, FundingItem.holder and Organization for free. Without this tier, 'one DirectoryAdapter per institution' is O(n_institutions) human work and the project cannot leave North America economically.
- **Sitemap.xml (via robots.txt Sitemap: directive) and hreflang alternates as the primary discovery mechanism** — The plan's directory discovery is search-and-verify over guessed paths (/people, /faculty, localized variants). Sitemaps give the authoritative, complete URL inventory with <lastmod> — which simultaneously solves discovery, the completeness checksum, and freshness/change detection without refetching pages. hreflang alternates give the language-variant mapping deterministically instead of language-detecting sampled pages.
- **Subdomain enumeration via Certificate Transparency (crt.sh) and passive DNS, plus Common Crawl's host index** — The corpus's own failure — eecs.yorku.ca 404s, the real host is lassonde.yorku.ca — is a solved problem: CT logs enumerate every subdomain of yorku.ca that ever had a cert. alt_domains[] is currently 'ROR/Wikidata links field', which lists one or two domains and never department hosts. This is the deterministic fix for the single most common discovery failure.
- **Schema.org / JSON-LD Person, Organization and hCard microdata extraction before any CSS-selector work** — Many university CMSes (Drupal, Sitecore, TerminalFour, Wagtail) emit structured Person markup with name, jobTitle, email, affiliation, sameAs[] (which is literally ProfileLink). Parsing JSON-LD first is language-agnostic, layout-agnostic and survives redesigns — it is the cheapest genericity lever available and it is absent from the extraction plan entirely.
- **National / regional doctoral thesis registries as the professor→student edge source: theses.fr, DART-Europe, NDLTD, ProQuest Dissertations, DiVA, Cristin, NARCIS successors, CNKI, KAKEN/researchmap, Mathematics Genealogy Project** — The plan concedes students are near-unobtainable and that LabMember.start_year is NOT_FOUND across the corpus. Thesis registries are structured, public, legal, retrospective and carry advisor↔student pairs WITH dates and thesis titles — theses.fr alone covers every French doctorate including in-progress registrations. This turns the 'students' headline feature from lab-page scraping (~2 of 6 labs) into a real dataset for many countries, and gives alumni cohorts and completion times.
- **ORCID employments/educations sections and the ORCID annual bulk dump, not just ORCID-as-an-ID** — Appointment.start/end and Person.academic_pedigree are both marked 'hard'. ORCID's employment records are self-asserted, dated, organisation-normalized (ROR/GRID-linked) and downloadable in bulk — the only structured global source for exactly those fields, including industry roles (a professor listing 'Google DeepMind, 2019-2024'). The domain model uses ORCID only as a join key and throws away its most valuable payload.
- **Grant/award registries with PI names and amounts: NIH RePORTER, NSF Award Search, UKRI Gateway to Research (API), CORDIS/OpenAIRE, DFG GEPRIS, SNSF P3, ARC/NHMRC, JSPS KAKEN, NSERC awards search** — FundingItem.holder and 'professor can top up (grant capacity)' are marked hard/unobtainable, yet these registries publish PI, project title, amount, start/end and often named collaborators and industry partners as structured open data with APIs. This is the single best proxy for 'can this professor actually fund me', is per-country adapterable exactly like the CRC/CIFAR cross-check pattern already in carry_forward, and is completely absent from the source list.
- **Crossref Funder Registry + award numbers on publications, and paper-level acknowledgement/affiliation footnote parsing** — 'Corporate funder of a lab is essentially never published' is only true of lab homepages. Papers carry funder DOIs, grant numbers, and dual affiliations. Multi-affiliation authorships in OpenAlex (professor listed with both a university and an industry lab on the same work) are a scalable, dated, evidence-backed source for the Organization/Appointment industry-link feature — far better than LLM parsing of bio prose.
- **OpenAlex as an enumeration source, not only an enrichment source: /institutions?filter=country_code:XX and /authors?filter=affiliations.institution.id:I…, plus the merged-IDs endpoint** — The pipeline crawls directories to find people. OpenAlex can enumerate every institution in a country (with ROR, domain, type, works count) and every author with a recent affiliation to it, before a single page is fetched. That gives an institution-independent baseline population to checksum directory harvests against, catches professors whose department page is broken or JS-only, and makes coverage_pct meaningful. Nothing in the plan uses it this way.
- **Academic vacancy aggregators and national portals: EURAXESS (API/RSS), jobs.ac.uk, AcademicPositions, FindAPhD, DAAD PhD database, Nature Careers, ScholarshipDb, plus institutional HR/vacancy feeds** — genericity_challenges correctly notes many countries have no individual-professor 'joining page' culture — but the plan then offers no alternative channel, so a country-scale run will report no_signal_found everywhere. Funded-PhD vacancies in Europe are advertised centrally with structured fields (deadline, funding, supervisor, eligibility) — exactly Opportunity + ApplicationCycle + FundingItem, already parsed. This is the highest-value missing source for non-North-American runs.
- **PDF and OCR handling as a formal rung in the fetch ladder (pdfplumber/PyMuPDF layout extraction, table extraction, OCR fallback), plus DOCX and image-embedded email** — WebSource has content_type but nothing downstream handles non-HTML. Faculty lists, admissions handbooks, funding tables, deadline calendars and CVs are routinely PDF-only, and in many countries the PDF IS the directory. Multi-column PDF layout and scanned scans break naive text extraction silently, producing scrambled names that then poison entity resolution.
- **Character-encoding detection and Unicode normalization policy (charset sniffing for windows-1256/1251, GB18030, Shift-JIS, EUC-KR; NFC normalization; confusable/homoglyph handling)** — Legacy university pages in Arabic, Russian, Chinese, Japanese and Korean still ship non-UTF-8 with wrong or missing charset headers. Mojibake at fetch time silently destroys name_native_script, breaks content_hash stability, and makes diacritic-bearing Latin names (Álvarez) non-matchable when NFC vs NFD differ between the directory and the personal page.
- **Conditional GET infrastructure: ETag / If-None-Match / If-Modified-Since storage per URL, plus per-host token-bucket rate limiter state and a persisted FetchQueue with backoff/retry/dead-letter** — The freshness model (7-14 day TTLs on recruiting signals) implies sustained daily refetching at country scale, but nothing in the schema stores an ETag, so every recheck is a full GET. There is also no entity for crawl budget, concurrency per host, or retry state — meaning politeness and cost are unenforceable and a crashed run cannot resume idempotently.
- **A Run/Batch ledger entity (run_id, pipeline_version, prompt_versions, model ids, start/end, per-stage cost, token spend, records touched, exit reason)** — CoverageRecord tracks targets, Claim tracks extractor+prompt_version, but nothing ties a set of claims to a single reproducible execution. Without a run ledger you cannot roll back a bad extractor version, attribute cost, compare two runs, or answer 'which claims came from the run where the Playwright rung was misconfigured'.
- **A text-canonicalization and diff-noise specification, with simhash/shingle similarity rather than raw content_hash** — change_tag (unchanged/NEW/CHANGED/disappeared) is the product's monitoring value, but content_hash over page text will flip on every fetch for any page containing a rotating news widget, a 'last updated' timestamp, a CSRF token, a session id, an analytics nonce or randomized related-links. Without a per-adapter noise filter and a fuzzy similarity threshold, the change queue is 100% false positives on day one and the user stops trusting it.
- **Entity-resolution blocking strategy and a merge/split audit trail entity** — 'Fuzzy name+institution matching' is O(n²): one country's academics is 10^5-10^6 records, i.e. 10^10+ pairs. You need explicit blocking keys (normalized surname metaphone + institution ROR + topic bucket), a scoring function, and — critically — reversible merges: an append-only MergeEvent with the evidence, because ORCID/OpenAlex IDs themselves get merged and split upstream and a wrong merge silently fuses two people's citation counts and recruiting signals.
- **DBLP's homonym disambiguation numbering ('Wei Wang 0001') and its person-record 'affiliation' notes** — DBLP is listed as a source but its most useful feature for the stated Bo Wang / Boyu Wang collision problem is its curated homonym suffixes and affiliation annotations — the only hand-curated disambiguation authority in CS. It should be a preferred merge key for CS, ranked above OpenAlex's machine disambiguation.
- **Per-institution email-pattern table derived only from observed mailto: addresses, plus an explicit no-guessing rule and MX/catch-all note** — Person.email is marked partial and 'has verified email' is a headline filter, yet many directories expose no address at all. An adapter field recording the observed pattern (first.last@dept.univ.tld, seen in N of M profiles) lets the UI say 'address not published; department pattern is X — verify before use' without ever fabricating a Claim. Currently the schema has no place for that distinction and the temptation to guess is unmodelled.
- **Wayback CDX API as a designed component (first-seen dates, prior-cycle baselines, recovery of vanished endpoints), with an explicit fallback for when archive.org is unavailable or the host is excluded** — The Wayback machine is mentioned twice in passing but it is the only way to date an undated recruiting statement (RecruitingSignal.datedness is otherwise just 'no year present'), to establish projected_from_prior_cycle deadlines, and to recover the WordPress endpoint that 404'd. It needs rate-limit handling and a documented degradation path, not a footnote.
- **Explicit modelling of translation in the evidence chain: language of the original, MT engine + version, and native-language classification prompts** — Claim carries quote + offsets, but if the extraction ran over a machine translation then the offsets point into a derived artifact, not the evidence. Nothing in WebSource or Claim records that a translation intervened or which engine produced it, so a mistranslated recruiting statement is indistinguishable from a correctly-read one at audit time.
- **arXiv (bulk metadata / OAI-PMH / S3 requester-pays) and paper-with-code style repo linkage as the 'current_directions' engine** — current_directions[] needs last-18-months output; OpenAlex indexing lags preprints by weeks-to-months, and in ML the preprint IS the publication. arXiv listings by author give same-week recency and the affiliation footnote, which is exactly the recency-weighted signal the ranking depends on.
- **Concrete non-Latin name-handling machinery: transliteration standards (pinyin, Hepburn, ALA-LC, BGN/PCGN), name-order metadata, patronymics, Spanish/Portuguese double surnames, Arabic al-/bin variants and married-name histories** — display_variants[] is a bag of strings with no generation rules. Without per-script transliteration and an explicit given/family disambiguation flag per source, a Chinese or Korean faculty roster cannot be joined to OpenAlex/DBLP at all — which is precisely the coverage gap that makes the tool least useful in the regions it claims to serve.
- **Snapshot storage design separate from SQLite rows (WARC or content-addressed gzip blobs with dedup), and SQLite WAL/single-writer discipline under a parallel fetcher** — 'SQLite as source of truth, git-attachable' collides with storing every fetched page for offset-based validation: a country run is 10^5-10^6 snapshots and multiple GB. SQLite is fine as the metadata store, but blobs belong outside it, git cannot diff it, and a multi-process crawler writing to one SQLite file will serialize on the write lock unless the architecture explicitly funnels writes through one process.

### Overconfident / risky (20)

- **Claim:** 'OpenAlex first (open API, global coverage, no blocking)' and BibliometricProfile fields largely marked reliable/partial
  - **Concern:** OpenAlex author disambiguation is fully automated and demonstrably wrong for common names (especially Chinese, Korean and Arabic names), producing both split profiles and merged profiles that fuse two people's citation counts. OpenAlex author IDs are also not stable — they get merged, which is why a merged_ids endpoint exists — so storing openalex_id as a durable join key without periodically resolving merges will silently corrupt the identity layer. Also, the polite pool requires a mailto parameter; without it you get the shared pool and de facto throttling. 'No blocking' is true; 'reliable' is not.
- **Claim:** 'Semantic Scholar showed 34 papers where the truth was 163 — per-source reliability must be stored'
  - **Concern:** That is almost certainly an author-disambiguation split (one person, several S2 author IDs), not a coverage difference. Diagnosing it as source unreliability leads to the wrong fix (a per-source reliability column) instead of the right one (resolve works via ORCID/DOI sets, never via name search, and union the author's S2 IDs). Storing 34 as 'Semantic Scholar's number' and showing it in the UI would present a disambiguation bug as a fact.
- **Claim:** Publication.authors[] ordered + author_position_of_person marked 'reliable', and first_author_junior_ratio as an authorship-risk signal
  - **Concern:** Author order is meaningless in the many fields that use alphabetical authorship (theoretical CS, cryptography, mathematics, much of economics), and Crossref/OpenAlex author ordering is itself frequently wrong for older or non-DOI records. Worse, first_author_junior_ratio requires knowing who is junior — which the plan elsewhere admits is unobtainable (no lab rosters, no start years). The metric is circular and will be confidently wrong in exactly the fields where it is most cited.
- **Claim:** 'distinct_coauthor_count — confidence: reliable'
  - **Concern:** It is only reliable relative to one source's works list, which the plan itself says can be off by 5x. A count derived from an incomplete set is not more reliable than the set. Marking any derived aggregate 'reliable' while its input is 'partial' is a confidence-inflation bug that will propagate into FitAssessment.confidence_of_score.
- **Claim:** 'robots_allowed / tos_note — confidence: reliable' and 'Respect robots.txt ... is what makes this publishable and defensible'
  - **Concern:** robots.txt is a crawling convention, not a licence and not a legal safe harbour; conversely, violating it is not automatically unlawful. Compliance with robots.txt says nothing about the site's Terms of Use, about database rights (sui generis DB right in the EU), or about data-protection obligations, which is where the actual exposure sits. Treating a boolean robots check as the legal posture conflates three separate regimes. Note also that Crawl-delay is not part of RFC 9309 and many hosts ignore/omit it, so 'obey crawl-delay' has no defined behaviour on most sites.
- **Claim:** GDPR handled via 'a clear scope statement and a documented takedown/erasure path'
  - **Concern:** Under GDPR the harder obligations are upstream of takedown: a lawful basis (a documented legitimate-interest assessment), and Art. 14 notification of data subjects when data is obtained from third parties — the disproportionate-effort exemption (Art. 14(5)(b)) is arguable but must be assessed and documented, not assumed. The household/personal-use exemption evaporates the moment the tool or its output is published. Storing derived, reputational judgements about named individuals (availability_status='departing', bandwidth_risk_note='VP at NVIDIA may limit bandwidth', fit verdicts) is profiling of identified persons and also carries plain defamation/injurious-falsehood risk if wrong — and the plan already documents that these are its stalest, least reliable fields.
- **Claim:** 'Students ... display only, never auto-message' plus lab-page-only collection is sufficient privacy posture
  - **Concern:** PhD students and predocs are not public figures in the way professors are, and many are early-career or from jurisdictions with strict rules. Publishing a lab page is consent to appear on that lab page, not to be aggregated into a queryable database joined with fellowship status, nationality aggregates, concurrent industry roles and inferred cohort years. The mitigation should include not retaining student records beyond aggregate counts by default, not just refraining from messaging them.
- **Claim:** 'Email + obfuscation_form ... de-obfuscate "fidler at cs dot toronto dot edu"' with 'has verified email' as a headline filter
  - **Concern:** Systematic de-obfuscation and storage of addresses is precisely the behaviour many university ToS and robots.txt forbid, and address-harvesting is separately regulated in some jurisdictions (CASL in Canada — the corpus's own target region — regulates address harvesting and use, independent of whether a message is sent). The deliberate defeat of an obfuscation measure is also the fact pattern most likely to be characterised as circumvention rather than ordinary crawling.
- **Claim:** Tiered escalation ladder with 'headless render (Playwright)' as the rung that handles blocked/JS sites
  - **Concern:** Cloudflare/Akamai/DataDome bot management fingerprints at the TLS/HTTP2 layer (JA3/JA4, header order) and via navigator.webdriver, so vanilla Playwright is blocked on exactly the sites where static HTTP already failed — the ladder has a hole at rung 3. The available fixes (stealth patches, undetected drivers, residential proxies, CAPTCHA solvers) are deliberate circumvention of a technical access control, which is a materially worse legal posture than the plan's conservative stance and should be an explicit, documented refusal rather than an unstated implementation detail.
- **Claim:** 'GitHub REST API (documented, rate-limited, ToS-clean)' — confidence reliable
  - **Concern:** Unauthenticated GitHub is 60 requests/hour, which is unusable at scale; authenticated is 5,000/hour and requires shipping or provisioning a token, which is an install-time dependency the 'clone and run' story doesn't account for. Secondary rate limits also throttle bursty search queries hard. 'Reliable' hides an operational prerequisite.
- **Claim:** 'completeness_checksum: site-declared counts vs harvested counts; a scrape returning 97 when the site claims 106 is provably incomplete'
  - **Concern:** Site-declared counts are themselves stale, often computed over a different population (including emeriti, adjuncts, staff, cross-appointees, or people the directory lists but the roster page does not), and sometimes hand-typed marketing copy. Treating any mismatch as proof of incompleteness will generate persistent false failures that train the operator to ignore the coverage system. It is a signal, not a checksum.
- **Claim:** 'quote_offsets — character offsets of the cited sentence inside the snapshot — the web analogue of :LINE', confidence reliable
  - **Concern:** Offsets are into normalized extracted text, so they are only valid for a specific extractor version and normalization pipeline. Any change to boilerplate removal, whitespace collapsing, Unicode normalization or the content selector silently shifts every stored offset in the corpus, and the validator will then report mass BROKEN_CITATION or, worse, validate against the wrong span. Offsets must be paired with a pinned extractor_version and a fuzzy quote-relocation fallback, otherwise this mechanism rots on the first refactor.
- **Claim:** Two-stage design: 'cheap deterministic enumeration for all, expensive multi-agent deep dive only for a user-approved shortlist'
  - **Concern:** This is circular with the parameter catalog. The fields the user would filter on to produce a shortlist — recruiting state, verbatim quote, enrolment_required, funding covers internationals, availability_status, contact_protocol — only exist at deep-dive depth. At enumeration depth the user can only filter on name, rank, institution and OpenAlex topics. Either the UI must hide every deep-only filter until depth is reached (and the plan's own 'no signal found ≠ never checked' rule must gate the score), or the deep dive must run on far more people than a 'shortlist'. As written, the first real user interaction will be ranking on fields that are uniformly null.
- **Claim:** 'A per-institution DirectoryAdapter ... adding a country means adding adapters, not editing the core'
  - **Concern:** Adapters are O(number of institutions), not O(number of countries) — the same sentence elsewhere concedes a country can mean 4,000+ institutions. Framed this way, the genericity mechanism is actually the scaling bottleneck and the main source of unbounded human maintenance. The plan needs an adapter-generation story (JSON-LD-first, CRIS-platform-first, LLM-proposed selectors validated against a held-out sample with an automatic accept/reject threshold) or the tool covers one region forever.
- **Claim:** 'Translate-then-extract' with the original stored as evidence and the translation as the searchable field
  - **Concern:** Machine translation reliably damages exactly the constructs that RecruitingSignal.state depends on: negation, modality, tense and conditional phrasing ('I will not be accepting', 'I may be able to consider'). An LLM classifying state from an MT string will be confidently wrong in a way no downstream validator can catch, because the validator only checks that the quote still exists in the original. Classification should run on the original language with a native-language prompt; translation is for display only.
- **Claim:** 'SQLite as the source of truth ... single file, git-attachable' with append-only per-field claim history plus snapshots
  - **Concern:** Per-field claim history over 10^5 people × ~40 fields × repeated observations is 10^7+ rows before snapshots; adding archived page content makes the file multi-gigabyte and binary, which git cannot diff and GitHub will reject. SQLite also has a single-writer lock, so a parallel fetch/extract pipeline must funnel all writes through one process (WAL plus a write queue) or it will serialize and appear to hang. None of this is fatal, but 'single file, zero-install, git-attachable' oversells it and will shape the architecture wrongly if taken literally.
- **Claim:** Recruiting-signal TTL of 7-14 days with polite per-host crawling
  - **Concern:** The crawl-budget arithmetic is never done. One university with 500 monitored professors at a courteous 1 request per 5-10 seconds is 40-80 minutes of sustained requests to a single host per cycle; ten universities on a 7-day TTL is a permanently-running crawler against a handful of hosts, which is exactly the traffic pattern that gets an IP banned regardless of robots.txt compliance. Conditional GETs, sitemap lastmod filtering, and per-host daily caps have to be designed in, not added later.
- **Claim:** 'LinkedIn is off-limits ... do not design around it' while alumni placement remains a headline feature backed only by lab alumni pages
  - **Concern:** Correct posture, wrong conclusion: the feature is then declared 'partial' rather than rescoped. It is also not true that lab alumni pages are the only public source — thesis registries, ORCID employments and OpenAlex affiliation-change-over-time all reconstruct placements legally and with dates. As written, the plan simultaneously bans the only source it identified and keeps the feature, which guarantees an empty column.
- **Claim:** 'pagination_pattern: record page/N or ?page= pattern' as the pagination model
  - **Concern:** Real directories use cursor/token pagination, POST-driven filters, GraphQL endpoints, infinite scroll backed by an undocumented JSON route, or return everything only under a specific per_page value with a silent server-side cap. Encoding pagination as a URL template will silently truncate results in precisely the way the Vector virtualized-list failure already demonstrated — and truncation looks identical to a small department.
- **Claim:** 'Person.availability_status ... regex + LLM over own page, department news, and destination-institution directory' as a hard eliminator filter
  - **Concern:** This is the plan's own highest-risk derived field, and it is being used as a hard eliminator that removes people from the user's consideration entirely. False positives (misreading an old leave notice, as with the 2021-2022 Zemel page) silently delete good targets, and there is no asymmetric-cost rule saying uncertainty must degrade to a warning badge rather than an exclusion. Hard gates should only be driven by claims at quoted_official confidence with a recent observed_at.

### Unresolved questions (12)

- Which two or three countries are actually in scope for v1? The answer determines whether the engineering effort goes into a Pure/CRIS adapter (UK, Nordics, NL, DE, AU), a national-portal adapter (EURAXESS, theses.fr, KAKEN), or bespoke WordPress/Drupal scraping (North America) — these are three different projects and only one can ship first.
- Is this a private tool that only you run locally, or a published open-source repo other people run? The GDPR lawful-basis, Art. 14 notification, retention and takedown obligations, and the defamation exposure of derived fields like 'departing' and 'bandwidth risk', all change completely between those two cases — and it also decides whether the harvested Ontario corpus can ship as seed data at all.
- What is the per-run budget in dollars and wall-clock hours? A country-scale enumeration plus deep dives has a token bill, a Playwright compute bill, and a politeness-bounded time floor (one host at 1 req/5s puts a hard lower bound on any run). Without a number, the two-stage gate cannot be calibrated.
- Are paid or key-gated APIs acceptable (Semantic Scholar API key, ProQuest, a Scholar proxy like SerpAPI), or must everything be free and keyless? This decides whether the bibliometrics layer is honest-but-thin or complete, and whether Google Scholar remains a manual-paste-only hole forever.
- Will you deliberately refuse anti-bot circumvention (stealth browsers, residential proxies, CAPTCHA solving) even when it means permanently losing Cloudflare-protected institutions? A written no here changes the fetch ladder's top rung from 'headless render' to 'record as blocked and queue for manual paste'.
- How many minutes per week of your own manual work is the pipeline allowed to require? Manual paste is the designed last rung for Scholar, login-walled forms and PDF-only lists; at country scale that queue can trivially exceed any human's capacity, and the scheduler needs a cap.
- What counts as 'done' for one university — a coverage percentage, a depth level, or a fixed budget of professors? CoverageRecord can report honestly but has no completion criterion, so the backlog is infinite by construction.
- Is scope restricted to CS/AI, or any field? Alphabetical authorship (theory CS, math, economics), non-English venue coverage, and the absence of arXiv-style preprint culture all break the recency and authorship-risk signals outside ML.
- What is your snapshot retention policy and your erasure workflow? Offset-based validation requires keeping archived copies of personal pages indefinitely, which is in direct tension with a right-to-erasure commitment; one of the two has to bend and the schema should encode which.
- Do you want a contact address and descriptive User-Agent published with the crawler (e.g. a project URL and an email that reaches you)? That is the single cheapest thing that turns 'unidentified scraper' into 'identifiable research tool with a takedown path', but it means receiving the complaints personally.
- For students specifically: do you need named individuals, or would per-lab aggregates (headcount by level, destination companies as counts, fellowship counts) satisfy the use case? Aggregates remove most of the privacy exposure and are far more obtainable than named rosters with years and prior institutions.
- What is your target application cycle and level (direct-entry PhD from a bachelor's? MSc first?)? If the answer is direct-entry PhD, GraduateProgram depth and the entry-route model are load-bearing for v1 and most of Europe is eliminated before any scraping happens — which should reshape the country list in question 1.

## Product & user

### Missing (10)

- **An Outreach entity: status (not_contacted / drafted / sent / follow_up_due / replied / declined / no_reply), sent_at, channel, which paper I cited, follow-up date, reply text, plus a 'chase list' view.** — The 95-parameter catalog models the world and models zero user actions. The applicant's actual daily loop is 'who have I emailed, who owes me a reply, who do I chase Monday.' Without this the user rebuilds a parallel spreadsheet within a week and the dashboard becomes a read-only artifact they stop opening. FitAssessment.next_action is a generated string, not tracked state, so it can never say 'you already did this.'
- **An Application entity keyed to GraduateProgram: materials checklist, fee paid, portal URL(s), referees assigned, submitted_at, decision. And a Referee entity on the user side (my 3 recommenders, which programs each has submitted to, per-letter deadlines).** — GraduateProgram models what the school demands; nothing models whether the user has done it. Reference letters are repeatedly called the real blocker, yet letters exist only as a program-side requirement count. The failure mode that actually loses cycles is a referee missing one program's portal link, and the model cannot represent that.
- **Program-as-the-unit-of-cost. The atomic purchase is one application (fee + SOP + letters) which covers N potential supervisors. Need a view: 'for this one application, here are the 3 best faculty to name in the SOP' and a per-application expected-value.** — The whole product ranks professors independently, but the user cannot buy professors — they buy applications. Two great professors in the same department cost one fee; two mediocre ones in different countries cost two fees, two SOPs and two letter rounds. Ranking at the wrong granularity produces a shortlist the user cannot execute against a fixed budget.
- **A per-professor outreach brief / evidence pack: 2-3 recent papers with one-line summaries, the specific overlap with the applicant's skills, their own verbatim quotes about what they value, and the contact_protocol sentence — rendered as one copyable block.** — This is the artifact that converts a shortlist row into a sent email. Every ingredient is already in the model (ContentItem buckets C and D, current_directions, contact_protocol quote) and nothing assembles them. Without it the user still spends 40 minutes per professor and the tool has saved discovery time only, which is the cheap half.
- **Total-cost and portfolio-sizing model: sum of application fees + test fees + transcript fees against a user budget cap, plus target counts per reach/realistic/fallback bucket with a warning when a bucket is empty or the whole list is too small.** — application_fee is listed as a 'sort' parameter, which is nearly useless — the decision is 'I have $600, which 6 applications?'. And portfolio_bucket is an enum with no target counts, so the tool will happily hand someone 12 reaches and 0 fallbacks, which is the single most common way applicants lose a year.
- **A base-rate / expected-yield layer: explicit priors on cold-email reply rates and per-program admit odds, used to tell the user 'a shortlist of 8 is too small' rather than implying each row is a live shot.** — The product's implicit promise is 'find the supervisor who will take you.' Real conversion is single-digit percent. Without stated base rates the user under-sizes their funnel and blames the tool when 8 perfect-fit professors all go silent.
- **Adjacency/recovery recommendations: 'X is closed/leaving — here are 5 people working on the same thing who are open', driven off topic tags + CollaboratorEdge + same-program membership.** — The model spends enormous effort detecting that a professor is unavailable (availability_status, closed_this_cycle, enrolment_required) and then leaves the user at a dead end. Elimination without substitution makes the tool feel like it is taking options away.
- **Alert delivery for change_tag: an email/RSS/ICS digest of 'shortlist changed this week', plus .ics export of every deadline and a CSV/Sheets export of the filtered table.** — Change detection with no delivery channel is inert — it only helps a user who was already going to open the dashboard. Freshness is the claimed differentiator, and a weekly diff digest is the cheapest, most shareable expression of it. Export is listed nowhere in the parameter catalog except window.print().
- **User-owned record state: pin / dismiss-with-reason / snooze-until, plus a free-text note with its own source (call with a current student, reply email).** — A country-scale list only becomes usable if it shrinks monotonically. With no dismiss, every session re-presents the same 400 rejected rows. The 'manual-only' confidence level is defined for advisor-quality fields but there is no place for the user to actually write down what they learned by asking.
- **A first-run path that works with zero configuration — a browsable prebuilt view (deadlines, funding, eligibility gates by program) before the user supplies a country, a ranked university list, GPA, language bands and eight priority weights.** — ApplicantProfile currently demands roughly a dozen manual-only inputs before the product produces anything. That is a total-loss onboarding for a tool a stranger clones. The universal answer to 'what does this do' has to be visible in ten seconds.

### Overconfident / risky (10)

- **Claim:** 'Recruiting status + eligibility + funding is the decision-making core and is obtainable at ~80% coverage.'
  - **Concern:** The project's own corpus contradicts this: only 20 of 104 professors had a verbatim recruiting quote. The realistic populated rate for the flagship field is ~20%, and the 'institutional accepting-students checkbox' existed at exactly one school. The product must therefore be designed for a world where 80% of rows read no_signal_found — which means the primary UI cannot be 'filter to actively_recruiting' (that yields a 20-row list biased toward professors who happen to maintain websites). Plan for ranking on indirect evidence (recent roster additions, lab news recency, new-lab status) as the default, and treat explicit quotes as a rare bonus.
- **Claim:** 'Nationality / export-control eligibility' as a first-class hard filter, and eligibility_verdict = blocked driving elimination.
  - **Concern:** An LLM classifying a scraped sentence into 'you are legally ineligible because of your citizenship' is the highest-harm error in the system: it is nationality-based exclusion, computed unreliably (the field is marked confidence: hard), it silently deletes viable options, and it is exactly the kind of output that gets a repo characterised as discriminatory. Show the quoted restriction verbatim next to the row; never let it hide a row by default, and never phrase it as a verdict about the user.
- **Claim:** min_grade and language thresholds listed as 'filter' kind, with normalization 'clearly marked as an estimate'.
  - **Concern:** Marking a conversion as an estimate does not help if the estimate is wired to a filter — the excluded rows are invisible, so the caveat is never read. Every gate built on an unreliable normalization (grade scale, availability_status, departing) must be a sort/annotation or a soft-hide with a visible 'N hidden by uncertain gates' counter, not a hard filter. Same for availability_status, which is explicitly the highest-risk derived field and would remove a perfect supervisor on a bad parse.
- **Claim:** 'Mentorship / equity posture ... explicit outreach to under-resourced regions correlates strongly with accepting non-traditional applicants' as a score-input.
  - **Concern:** This is an unevidenced correlation presented as a scoring feature, and the resulting behaviour — ranking named academics by how much DEI language they post, so applicants can target them — reads badly in both directions (as gaming, and as profiling professors by political signalling). Keep the A-E content buckets as browsable evidence for writing an email; do not turn bucket E into a numeric score component.
- **Claim:** bandwidth_risk_note, junior_first_authorship_ratio, lab_wellbeing, fit verdicts and staleness judgements as stored fields on named real people.
  - **Concern:** These are published evaluative judgements about identifiable individuals, generated by an LLM, with no right of reply. Aggregated into a shareable export or a repo they are defamation-adjacent and a guaranteed source of takedown mail. Constrain them to local-only user annotations, exclude them from any export or artifact intended to leave the machine, and make that a harness rule rather than a convention.
- **Claim:** Ship a 'deliberately thin students/companies slice' in v1 so the schema is exercised.
  - **Concern:** LabMember is the highest privacy exposure in the project (named grad students with fellowships, prior institutions, destinations and nationality-adjacent aggregates) and simultaneously the least obtainable (year_joined absent everywhere, alumni published by ~2 of 6 labs). A thin slice buys almost no user value while importing the full legal surface. Cut it entirely from v1; keep only aggregate lab headcount and roster-currency, which are lab facts rather than person records.
- **Claim:** Two-stage pipeline: cheap enumeration for all, expensive deep dive 'only for a user-approved shortlist'.
  - **Concern:** Chicken-and-egg: the fields the user needs to shortlist on (recruiting signal, funding, admitting routes, enrolment requirement) are exactly the ones only the deep dive produces. Enumeration yields name + title + areas, which is not enough to approve anything. The gate needs a middle rung — a cheap single-page fetch of the professor's own homepage for every enumerated person — or the user approves a shortlist essentially at random.
- **Claim:** Ship no personal seed data in the public repo (option B), while relying on the repo being clonable and demoable to attract users.
  - **Concern:** These two goals are in direct conflict and the foundation does not reconcile them. A repo whose demo is 'run a multi-hour scrape against 40 universities and hope' converts nobody. The resolvable version: publish the non-personal layer — program deadlines, funding packages, direct-entry rules, language bands per program — as the public dataset (organisational facts, low privacy risk, genuinely useful standalone), and keep person-level data generated locally.
- **Claim:** OpenAlex-first bibliometrics powering current_directions from 'the last 18 months'.
  - **Concern:** OpenAlex lags on arXiv preprints, which is where CS current direction actually lives, and its author disambiguation is noisy for common names — the exact collision class the identity section worries about. Recency detection should lean on arXiv listings and the professor's own publications page, with OpenAlex used for volume, not for what-they-work-on-now.
- **Claim:** 'Nothing here has been sent anywhere — the actual emailing is yours to do' as the sufficient ethical guardrail, shipped alongside contact_protocol and an outreach layer.
  - **Concern:** The disclaimer covers automation but not scale. A tool that produces 200 ranked professors with per-person talking points is an industrial cold-email generator regardless of who presses send, and mass templated outreach is precisely what makes faculty stop reading applicant email. The product should cap or discourage bulk drafting, refuse to generate N near-identical emails, and surface do_not_email/form_only as a blocking state in the outreach UI, not just a facet.

### Unresolved questions (9)

- Is the user you, once, for the 2026-27 cycle — or strangers, repeatedly? A one-shot personal decision tool and a shipped open-source product have almost opposite designs (the first should skip identity resolution, conflict policy, adapters and scoring entirely and just get you 40 good rows fast).
- What is the date by which the tool must be useful, relative to your own deadlines? If deadlines are ~5 months out, the honest comparison is 'build this' vs 'spend 3 weeks doing 60 professors by hand', and the hand path probably wins for you personally while the tool wins only if it serves others.
- Which field(s) of study? CS-only makes arXiv/DBLP/OpenAlex viable and the whole source strategy coherent; 'all disciplines' invalidates most of the bibliometric and lab-page assumptions and roughly triples adapter work.
- Are you actually targeting a December application, or the pre-PhD/RA/internship route 12 months earlier that the corpus identifies as the higher-probability path? These are different products — the second is an opportunity tracker keyed on Opportunity and rolling windows, not an admissions dashboard keyed on ApplicationCycle.
- How many applications can you afford in fees and letter-asks? That number, not a university ranking, should drive the size and shape of the output.
- What is the success metric — replies received, offers, or GitHub stars? Optimising for stars points at publishing the non-personal deadline/funding dataset; optimising for offers points at outreach tracking and a much smaller professor set.
- Are you willing to publish a repo containing evaluative judgements (fit, bandwidth risk, staleness) about named real academics, and to handle erasure/takedown requests? If not, that constraint has to be a build-time rule now, not a policy note later.
- Who maintains 40+ DirectoryAdapters when the sites change — and what happens to a shipped tool the first month half of them break silently? Is there an adapter-health surface, or does the tool just quietly return fewer professors?
- Is the misspelled repo name ('proffessor') intentional? It is the first thing a visitor sees, it kills search discoverability, and it undercuts a project whose entire pitch is verification discipline.

## Multi-agent architecture & portability

### Missing (19)

- **Run / Task / Checkpoint entities in the schema (run_id, params, budget, status; task = target × stage × attempts × last_error × idempotency_key)** — The foundation has CoverageRecord (about targets) but nothing about job state. Every prior session died at context exhaustion mid-run. Resumability must come from `SELECT * FROM task WHERE state='pending'`, not from the orchestrator's memory. This is also the single change that makes the orchestrator LLM-optional: the state machine lives in SQLite, the model just drains a queue. Without it, 'multi-agent' means 'unresumable'.
- **An ExtractionCache keyed by (snapshot_content_hash, prompt_version, model_id, schema_version)** — This is the biggest cost lever in the whole project and it is nowhere in the foundation. WebSource.content_hash exists but is framed as validator support, not as the LLM cache key. With this key, a re-run over 500 professors where 480 pages are unchanged costs ~4% of the first run. Without model_id and prompt_version in the key you cannot invalidate after a prompt edit; without content_hash you re-pay for every unchanged page every cycle.
- **A field→extractor mapping so a prompt change re-extracts only the affected fields** — Claim already records extractor{agent, model, prompt_version}, but nothing maps 'I changed the recruiting-signal prompt' to 'invalidate exactly these 1,200 claims'. Without it every prompt tweak is a full re-run, which in practice means prompts never get improved.
- **A mandatory `NOT_FOUND` / `ABSTAIN` value in every extraction output schema, distinct from a null** — The foundation correctly insists 'no_signal_found' ≠ 'not_recruiting' at the RecruitingSignal level but never pushes that discipline into the LLM's own output contract. A model with no abstain token will confabulate to fill a required field. Abstain is also the escalation trigger for the cheap→strong model cascade.
- **Structural quote verification: the model returns the exact quote, deterministic code locates it in the snapshot (normalized substring search) and DROPS the claim if it is not found. Never ask the model for character offsets.** — The foundation's anti-hallucination story is still mostly prose ('never invent', 'cite a URL + date'), inherited from a prompt-era prototype where it demonstrably failed (the Zhijing↔Dan Roth co-authorship survived across five files). Model-supplied offsets drift and paraphrases pass a human eye. A literal-substring gate is cheap, deterministic, provider-independent, and mechanically kills fabricated evidence at ingest rather than at audit.
- **A synthesis-stage entity guard: no proper noun, number, URL, or date may appear in a synthesis output unless it appears in the declared upstream artifact set** — The one confirmed hallucination in the corpus was introduced at synthesis, not extraction, and the auditor caught it only by hand. Extraction-level evidence rules do not cover the node that invents.
- **A per-provider structured-output adapter matrix (Anthropic tool-use, OpenAI response_format/json_schema, Gemini responseSchema, GBNF grammar for local models) plus a declared 'minimum capable model'** — Option B (CLI core + provider adapter) is the right call but 'thin provider adapter' hides the real work: schema enforcement mechanisms differ, and prompts that rely on Claude habits (XML tags, long-context dumping, implicit instruction-following depth) silently degrade elsewhere. Portability is a property of the prompt+schema contract, not of an adapter file.
- **A golden eval set with per-model pass thresholds, plus recorded LLM cassettes for offline deterministic CI** — 'Portable to other LLMs' is currently an aspiration with no test. The Zhijing VERIFIED file and the 104 hand-profiled dashboard records are already labelled ground truth — turn them into a conformance suite that any candidate model must pass. Cassettes also make CI free and deterministic; otherwise every PR costs money and flakes.
- **Safety enforced in the Python layer: an allowlisted HTTP client (GET/HEAD only, no auth headers, no form POST, no mail transport), a path-jailed writer, robots+crawl-delay per host** — The foundation leans on settings.json because 'permission rules are enforced by Claude Code itself'. That enforcement does not exist in any other host. On the day this ports to a plain CLI or another LLM, the entire safety boundary evaporates. settings.json must become defense-in-depth over a Python boundary, not the boundary.
- **DirectoryAdapters as plain data files (YAML/JSON) with a JSON Schema and a validation test, plus an adapter-authoring/repair agent role** — Adapters are the community contribution surface and the genericity mechanism; if adding Germany means editing Python, nobody contributes. Also: the highest-value genuinely-LLM task in this whole system — 'look at this unfamiliar directory and write/repair its adapter' — is not in the proposed agent topology at all, while several low-value nodes are.
- **Conditional GET (ETag / If-Modified-Since), a per-host token bucket, and a global concurrency cap** — A 304 is a free freshness check. The re-verification model (TTL sweeps every 7–14 days over hundreds of pages) is only polite and affordable if most rechecks are conditional. Nothing in the foundation mentions HTTP caching.
- **Boilerplate-stripped content hashing for change detection (hash the extracted main content, not the raw HTML)** — Raw-HTML hashes churn on CSRF nonces, ad slots, 'today's date' widgets and rotating carousels, so every professor reads as CHANGED and the diff feature becomes noise. The corpus already found one site with ~7,500 chars of nav before the bio.
- **A cheap deterministic pre-score to rank the deep-dive queue, computed from directory-level fields only** — The two-stage gate is right, but the gate as described is user approval — which does not survive 'all universities in this country'. Nobody approves 10,000 rows. Deep-dive spend must be allocated by an automated cheap score, with human approval applied to the top-N slice only.
- **Cost/budget as a first-class run parameter with per-stage accounting and a hard stop** — Not a single field in the foundation records tokens or dollars, yet cost is named as a design constraint 'from day one'. Attribute cost to Claim.extractor and WebSource.fetch_method so you can answer 'the audit agent is 60% of spend' — which it will be if it samples 100% of recruiting signals at opus tier.
- **Erasure/redaction command (`purge --person <id>` cascading to all claims, snapshots and exports) and a do-not-collect list** — The open_decisions acknowledge GDPR and a 'documented takedown path' but no mechanism exists. With append-only claim history and content-addressed snapshots, erasure is architecturally hard and must be designed in now, not retrofitted.
- **Model-tier selection expressed in portable config, not in .claude/agents frontmatter** — Per-role model tiering is cited as the affordability mechanism, but as implemented in career-scan it is a Claude Code frontmatter feature. If tiering lives only there, the ported CLI runs everything on one model and the cost argument collapses.
- **Observability: structured run log, per-stage counters, failure-taxonomy histogram, and a `--dry-run` / `--estimate` mode** — At country scale you cannot debug by reading transcripts. You need 'of 4,120 fetches: 3,001 ok, 610 js_only, 300 404, 209 bot_block' before you commit LLM spend.
- **SQLite concurrency model (WAL, single writer, workers return rows not connections) and deterministic ID minting with a merge/unmerge audit log** — Parallel agents plus one SQLite file is a lock-contention and corruption path. And identity merges must be reversible — an ORCID mismatch discovered later must be undoable without a full re-scan.
- **An explicit export contract test between the DB and the dashboard JSON (schema version + fixture)** — The dashboard is a second consumer with its own shape. The prior dashboard silently dropped professors on a name typo; a contract test is what prevents a repeat in the JSON boundary.

### Overconfident / risky (14)

- **Claim:** Agent topology: 'a discovery agent (resolve identity + confirmed links), parallel per-source agents (bibliometrics, lab/roster, openings/admissions, content/social), and a synthesis agent'
  - **Concern:** This is the prompt's 5-file output structure promoted to an agent boundary, which is agents-for-the-sake-of-agents. Link discovery is href extraction + host classification — regex and a dict, no LLM. Bibliometrics is an OpenAlex/Crossref/DBLP API client — no LLM. GitHub is REST — no LLM. Only ~2 of the 5 nodes are genuinely LLM-shaped (content classification, synthesis/conflict adjudication), and the highest-value LLM task (adapter discovery/repair on an unfamiliar directory) is missing entirely. Correct split criterion is not 'output file' but 'does this need unbounded tool exploration?' — subagent if yes, plain stateless typed call if the input is a fixed text blob and the output is a fixed schema. Per-professor extraction at N=hundreds should be a batch worker loop, not N subagents each paying 2–5k tokens of system/tool preamble.
- **Claim:** 'The model never gets to originate a number' carried forward as the governing invariant
  - **Concern:** It is already violated by the design: FitAssessment components like topic_match, mentorship_posture and bandwidth_risk are inherently model-derived. Shipping a slogan the system breaks on day one is worse than no slogan. Restate it precisely: the LLM may emit an ordinal label from a closed enum, justified by a verified quote; deterministic code maps labels→numbers and does all arithmetic. Counts, amounts, dates and citations remain script-only.
- **Claim:** 'SQLite as the source of truth (single file, zero-install, git-attachable, real joins)'
  - **Concern:** SQLite is a binary blob — 'git-attachable' is true but 'git-diffable' is not, and the stated motivation for storage was that prose files 'cannot join, dedupe or diff'. You get joins but lose review-time diffs. Cleaner: adapters + prompts + a deterministic JSONL export are the git source of truth; SQLite is a derived, rebuildable index. Otherwise every PR carries an opaque binary and merge conflicts are unresolvable.
- **Claim:** 'OpenAlex first (open API, global coverage, no blocking)' and 'a matching ORCID/OpenAlex ID as decisive for merging'
  - **Concern:** Two problems. (a) OpenAlex is rate-limited and expects a polite-pool mailto; unauthenticated bursts get throttled — 'no blocking' is overstated. (b) OpenAlex author disambiguation is genuinely weak: author IDs merge and split, and common names in some regions are systematically conflated. Treating an OpenAlex author ID as *decisive* will silently merge two people — exactly the Bo Wang / Boyu Wang failure the design claims to fix, now with false confidence. ORCID is decisive when self-linked from the person's own page; OpenAlex should be evidence, not a merge key. Likewise 'ORCID public API by name+affiliation' is a low-precision search and must never auto-attach an ID.
- **Claim:** 'BibliometricProfile 1-1 Person' alongside 'store one row PER source, never a blended number'
  - **Concern:** Direct schema contradiction. It must be Person 1-N BibliometricProfile keyed by source, or the 'never blend' rule is unimplementable and someone will write an averaging query.
- **Claim:** 'Respect robots.txt, descriptive User-Agent, public pages only … is what makes it publishable, contributable and defensible'
  - **Concern:** Robots compliance is a norms question, not a lawful basis. Under GDPR the exposure is that you are building profiles — including inferred judgements like bandwidth_risk, availability_status and fit verdicts — on named EU individuals, with Art. 14 notification duties and profiling provisions attached, and 'publicly available' is not an exemption. Conflating ToS hygiene with legal defensibility is the risky part. Minimum posture: local-only storage, no republication of personal records, a working erasure command, an explicit lawful-basis note, and real advice before any hosted or shared deployment. I am not a lawyer and this needs one.
- **Claim:** Option B for students: 'lab pages plus bibliometric inference — recent junior co-authors as probable current students', as a labelled second layer
  - **Concern:** This is the riskiest feature in the product and the label does not neutralize it. It manufactures unconsented supervisory-relationship records about the most junior, least public people in the dataset, from an inference the corpus itself proved unsound ('co-authorship does not imply supervision'; one person appeared on two lab rosters and had actually graduated). Recommend: off by default, never persisted, computed at view time only, and excluded from any export.
- **Claim:** 'The validator re-opens the snapshot to confirm the quote' as the evidence guarantee
  - **Concern:** That proves only extractor fidelity — that the model did not invent text relative to what was fetched. It says nothing about whether the fact is true, current, or whether the page itself was wrong (Zemel's page asserting a 2021-2022 leave; Urtasun's 5-year-stale 'looking for motivated students'). A green validator badge will be read by users as 'true'. These are two separate checks (faithfulness vs. currency) and must be two separate, separately-rendered states.
- **Claim:** Carrying the ROLE ethics/provenance preamble ('never invent', 'cite a URL + date for every item') verbatim as the agent system-prompt header
  - **Concern:** It is prose with zero enforcement, and it is the exact text that was in force when the corpus produced a hallucinated co-authorship and a file truncated mid-word at item 13. Ship it as documentation, but do not count it as a control, and do not let its presence substitute for the substring gate + schema enum + completeness check that actually do the work.
- **Claim:** 'Cap agent returns at ~10 lines' as the context-economics mechanism at country scale
  - **Concern:** 10 lines × 300 professors is 3,000 lines back into the orchestrator. The budget must be per-run, not per-agent: workers should return a task id and a status enum only, writing all output to the DB. The orchestrator should never see per-professor prose.
- **Claim:** The 5-file DAG (FILE 1 → FILE 2 needs the confirmed X handle) as pipeline topology
  - **Concern:** The X/Twitter node requires a logged-in session, which option A of the legal posture hard-blocks. Making it a DAG node means a large fraction of runs have a permanently failed dependency and a degraded synthesis. Social must be an optional enrichment branch whose absence is normal, not a pipeline stage.
- **Claim:** 'A stranger can clone the repo, run one command and open a working dashboard'
  - **Concern:** Not achievable as specified: it needs Python, Playwright browser binaries, at least one LLM API key, and network access to a dozen hosts. State the real install honestly and ship an `--offline --demo` mode backed by fixtures so the clone-and-run promise is true for the demo path and only the demo path.
- **Claim:** Adversarial evidence-auditor sampling '100% of recruiting signals, funding amounts, deadlines and eligibility claims' at opus tier
  - **Concern:** That is the most expensive model reading the most numerous fields; at country scale it plausibly exceeds the rest of the pipeline's cost combined. Make the sampling policy budget-aware and risk-weighted (100% only for claims that flip an eligibility gate or enter the top-N shortlist), and let the deterministic validator absorb everything mechanically checkable first.
- **Claim:** Per-role model tiering plus the two-stage gate 'is what makes it affordable'
  - **Concern:** Both are Claude Code-shaped and neither is the dominant lever. The dominant levers are: (1) never send raw HTML to a model — send boilerplate-stripped text with a hard byte cap; (2) skip the LLM entirely when the content hash is unchanged; (3) batch many targets per call against a cached shared system prompt. None of these three appear in the foundation.

### Unresolved questions (10)

- What is the hard budget for one full run — dollars and wall-clock hours? Everything about agent granularity, model tiering and the size of the deep-dive shortlist follows from this number, and nothing in the foundation states it.
- What is v1's literal scale target: Ontario-sized (8 institutions, ~150 professors) or a real country (thousands)? These are different architectures — the first tolerates per-professor subagents, the second demands a queue-drained batch worker.
- Which non-Claude providers must v1 actually pass, and is a local/offline model (Ollama, llama.cpp) in scope? Local models cannot do reliable tool-use-style structured output without grammar constraints, which changes the prompt contract.
- Is this a personal tool that only you run, or a published product other people will run against real people's data? That single answer decides GDPR posture, license, whether adapters ship, and whether any personal record can be committed.
- When the Claude Code skill and the CLI disagree, which is the product? Specifically: does the skill shell out to the installed CLI (my recommendation), or does it vendor its own copy of the scripts under .claude/skills/? Vendoring guarantees drift.
- Does the Claude Code skill need to work on a machine with no Python? If yes, the deterministic layer cannot be Python and that inverts option B.
- What is the acceptable human-in-the-loop load — how many rows are you willing to approve per run, and would you accept fully automatic shortlisting if the pre-score is explainable?
- Past what age does a recruiting signal get hidden rather than shown with a penalty? A displayed-but-penalized stale green signal is how the prior dashboard misled; a hard cutoff is a product decision, not a technical one.
- Are you willing to ship v1 where 'unknown' is the modal value in half the columns? The honest-nulls design is right, but it looks broken on first open, and there is no plan for what an empty-heavy dashboard should say to a new user.
- Do you want cross-model disagreement measured and surfaced as a per-claim confidence signal? It is the cheapest real portability test you can run, but it multiplies extraction cost by the number of models.
